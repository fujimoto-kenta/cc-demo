# デモパターン集（発表者向け）

聴き手は「ChatGPT のチャットは使っているが、Claude Code は初めて」という人たちを想定しています。
どのデモでも、伝えたい違いは同じです。

> **ChatGPT は「答えを返す」。Claude Code は「自分で読んで、手を動かして、確かめる」。**
> 人はコードを貼り付けない。人は結果を確認して判断する。

## 早見表

| # | デモ | 時間 | 難易度 | 出発ブランチ | 一番伝わること |
| --- | --- | --- | --- | --- | --- |
| 1 | コードを読んで説明させる | 3分 | 低 | `demo/fixed` | 貼り付け不要。自分で探して読む |
| 2 | バグを直す | 5分 | 低 | `demo/buggy-app` | 原因の説明 → 修正 → テストで確認まで自走する |
| 3 | 新機能を作る | 8分 | 中 | `demo/fixed` | Plan mode で計画をすり合わせてから作る |
| 4 | テスト結果を Artifact で共有 | 4分 | 低 | `demo/fixed` | ターミナルの外に「共有できる成果物」を出せる |
| 5 | ブラウザを操作させる（MCP） | 4分 | 中 | `demo/fixed` | 外部ツールとつなぐと、できることが広がる |
| 6 | Plugin を作って配る | 8分 | 中 | `main` | 自分の工夫をチームに配れる |
| 7 | Issue から PR まで（GitHub 連携） | 6分 | 中 | `demo/buggy-app` | 普段の開発フローにそのまま乗る |
| 8 | コード以外の仕事（資料・ドキュメント） | 4分 | 低 | どこでも | エンジニア以外にも使い道がある |
| 9 | 自動化（`claude -p`） | 3分 | 中 | `demo/fixed` | スクリプトや CI に組み込める |

**1時間の枠で選ぶなら**: 1 → 2 → 4（合計約12分）が鉄板。時間があれば 3 か 5 を足す。
**エンジニア中心なら**: 2 → 3 → 6 → 7。
**エンジニア以外が多いなら**: 1 → 4 → 8。

すべてのデモの前に、作業用フォルダで一度 `claude` を対話起動し、「このフォルダを信頼する」を承認しておくこと（[setup.md](setup.md) 参照）。

**権限モードについて**: v2.1.283 以降、新しいセッションは **Auto モード**（危険な操作だけ自動でチェックし、それ以外は確認なしで進む）で始まる。
「人が確認して許可する」様子を見せたいデモ（2、3、6）は `claude --permission-mode default`（Manual）で起動する。

## 1. コードを読んで説明させる（3分）

**ねらい**: ChatGPT との一番の違い「コードを貼らなくてよい」を最初に体感してもらう。

```text
このリポジトリは何をするもの？ 構成と、TODOがどこに保存されるかを初心者向けに説明して
```

```text
@public/app.js の render 関数がやっていることを、図解するつもりで説明して
```

**見せどころ**

- Claude が自分でファイル一覧を見て、必要なファイルだけを読んでいる様子（ツール実行の表示）
- `@ファイル名` で読む場所を指定できること

**話すこと**: 「ChatGPT なら、どのファイルを貼るかを人が考える必要があった」

---

## 2. バグを直す（5分）

詳しい台本は [demo-script.md](demo-script.md) の手順 5〜7。

```text
「未完了」フィルタ中に「散歩する」を削除したら「本を読む」が消えた。
原因を特定して直して。再発しないようにE2Eテストも追加して
```

**リハーサル結果**: 約45秒。原因の説明、ID ベースへの修正、回帰テストの追加、修正前にテストが失敗することの確認までを自走した。

**話すこと**: 症状だけを伝えればよい。「原因を特定して」「テストも」と完了条件を付けるのがコツ。

---

## 3. 新機能を作る（8分）

**ねらい**: 大きめの変更は「いきなり書かせない」。Plan mode で計画を確認してから進める流れを見せる。

1. Shift+Tab で Plan mode にする（または `/plan` と入力）
2. 依頼する

   ```text
   TODOに期限日を設定できるようにしたい。追加フォームで日付を任意で入力でき、
   一覧に期限日を表示し、期限切れの未完了TODOは赤く強調して。
   既存の動作を壊さないこと、E2Eテストも追加すること。日付に依存するテストは時計を固定して書いて
   ```

3. 出てきた計画にコメントする（例: 「期限日は今日より前を選べないようにして」）
4. 承認して実装させ、`npm start` で画面を確認する

**見せどころ**

- 計画の段階で人が方針を直せる
- 「日付に依存するテストは時計を固定」のような品質の指示も通る

**参考実装**: `demo/feature-due-date` ブランチ（リハーサルで Claude が作ったもの）

---

## 4. テスト結果を Artifact で共有（4分）

**ねらい**: ターミナルの文字の羅列ではなく、上司やチームにそのまま送れる Web ページを出せることを見せる。

```text
E2Eテストを実行して、結果をチームに共有できるArtifactにまとめて
```

プラグイン `cc-demo-kit` を入れていれば次の1行でも同じことができる。

```text
/cc-demo-kit:test-report
```

**見本**: [cc-demo E2E テスト結果](https://claude.ai/artifact/GP2hHL3LxPEGgru1CWF28o)（期限日ブランチで実行した15件の結果。共有設定は発表者が行う）

**注意**

- Artifact は**対話モード**でのみ使える（`claude -p` では作れない）
- claude.ai アカウントでのログインが必要（API キーでは不可）
- 作られたページは最初は自分だけが見られる。共有はページ右上の Share から

**話すこと**: 「ChatGPT の Canvas のように、成果物を別ウィンドウで見せられる。しかも元データは実際に実行した結果」

## 5. ブラウザを操作させる（Playwright MCP、4分）

**ねらい**: MCP で外部ツールをつなぐと、Claude が「画面を見て確かめる」ことまでできる。

事前に `npm start` でアプリを起動しておく。リポジトリの `.mcp.json` に Playwright MCP を設定済み（初回は承認を求められる）。

```text
Playwright MCPで http://localhost:3000 を開いて、TODOを3つ追加し、1つを完了にして、
画面の状態を報告して。ブラウザのコンソールにエラーが出ていないかも確認して
```

**見せどころ**

- Claude が実際にクリックや入力をして、結果を報告する
- リハーサルでは、コンソールに favicon の 404 エラーが1件出ていることを見つけた。続けて「直して」と頼むと修正までできる

**事前準備**: `npx @playwright/mcp@0.0.83 install-browser chrome-for-testing`（MCP 用のブラウザ。テスト用とは別版）

## 6. Plugin を作って配る（8分）

**ねらい**: 自分で育てた手順（Skill）や設定を、チームに1コマンドで配れることを見せる。

完成形は `plugins/cc-demo-kit/` にある。ライブでは「既存の `.claude/skills` をプラグインに変換する」流れが分かりやすい。

```text
.claude/skills/run-e2e をプラグインにしたい。plugins/my-kit に plugin.json を作って移して。
JavaScriptを編集したら構文チェックするHookも入れて。最後に claude plugin validate で検証して
```

確認と配布:

```bash
claude plugin validate ./plugins/my-kit
claude --plugin-dir ./plugins/my-kit          # インストールせずに試す
```

```text
/plugin install cc-demo-kit --marketplace fujimoto-kenta/cc-demo   # 公開済みのものをインストール
/plugin                                                            # 入っているプラグインを確認
```

**見せどころ**

- Skill は `/プラグイン名:スキル名` で呼べる（例: `/cc-demo-kit:run-e2e`）
- Hook は「必ず実行される」。わざと構文エラーを入れさせると、Hook がすぐ指摘して Claude が直す

**話すこと**: 「プロンプトの工夫を個人のメモで終わらせず、チームの資産にできる」

---

## 7. Issue から PR まで（GitHub 連携、6分）

**ねらい**: 普段の開発フロー（Issue → ブランチ → PR → レビュー）に Claude Code がそのまま乗ることを見せる。

`gh` コマンドで GitHub にログイン済みであること。

```text
フィルタ中に削除すると別のTODOが消えるバグをGitHubのIssueとして登録して
```

```text
さっきのIssueを直して。ブランチを切ってコミットし、Issueを閉じるPRを作って
```

```text
/code-review
```

**発展**: `/install-github-app` で GitHub Actions を設定すると、Issue や PR のコメントで `@claude` と書くだけで Claude が作業する（[team-setup.md](team-setup.md) 参照）。

## 8. コード以外の仕事（4分）

**ねらい**: エンジニア以外の聴き手に「自分の仕事でも使える」と思ってもらう。

```text
/slides このリポジトリで今日やったことを、非エンジニア向けに5枚で
```

```text
docs/ の内容をもとに、新メンバー向けのオンボーディング資料を作って
```

```text
このフォルダのCSVを集計して、部署ごとの傾向をグラフ付きのArtifactにして
```

**話すこと**: 「ファイルを読める・コマンドを実行できる AI」は、資料作成やデータ整理にも効く。

---

## 9. 自動化（`claude -p`、3分）

**ねらい**: 対話しなくても、スクリプトや CI から呼び出せることを見せる。

```bash
claude -p "public/ のコードを読んで、アクセシビリティ上の問題を3つ挙げて" > a11y.md
git diff | claude -p "この差分のコミットメッセージを日本語で1行で"
```

**話すこと**: 「毎回同じ指示を打つ作業は、`-p` でスクリプトにできる」

## ChatGPT ユーザーからよく出る質問

| 質問 | 答え方 |
| --- | --- |
| ChatGPT にコードを貼るのと何が違う？ | 貼らなくても自分で探して読む。編集・実行・テストまでやる |
| 勝手にファイルを壊されない？ | 危険な操作は実行前に自動でチェックされ、Manual モードなら編集やコマンドのたびに確認が出る。git で管理していれば元に戻せる。`Esc` 2回で巻き戻しもできる |
| 会話の内容は学習に使われる？ | プランや設定による。社内利用の前に管理者と確認する（[team-setup.md](team-setup.md)） |
| ChatGPT の「カスタム指示」にあたるものは？ | `CLAUDE.md`。プロジェクトごとに置ける |
| GPTs にあたるものは？ | Skills と Plugin。手順書をファイルで置き、チームに配れる |
| Codex を使っている | `/import codex` で Codex の設定（指示ファイル、MCP など）を取り込める |
